# HANDOFF — claude-conductor

The one file that starts a claude.ai session for conductor work. Read it, then `README.md` (how conductor works) and `claude-ai-new-project.md` (how a project uses it, ending with the planner's vocab). Every conductor prompt updates *Status* and *Open* before committing; nothing else in this file changes without a reason.

## How work on conductor flows

- Matt discusses with a claude.ai session linked to the box. The session reads and writes `C:\Code\claude-conductor` over the bridge. It writes each prompt to `prompts/NN_name.md` (git-ignored).
- Matt pastes or names the prompt in a Claude Code session in this repo. Conductor never runs its own queue: its prompts always go this way, by hand.
- CC writes `reports/NN_name_report.md` (git-ignored) and ends with `Report written to <path>`. Matt says "report's in", and the session reads it.
- Testing uses the sandbox only: `C:\Code\conductor-sandbox` and `C:\Code\conductor-sandbox-control`.
- This replaced the fractal project's relay through Google Drive and hand-placed files. Drive is not part of this workflow, and nothing should reintroduce it as a relay. (A project's *Storage* policy in `claude-ai-new-project.md`, Drive as the one home for some large files, is a separate thing.)

## Design decisions (settled 2026-10-15)

- **Three roles.** The claude.ai planner works files-only. The conductor daemon owns every process. Executors are headless CC run with `--dangerously-skip-permissions`.
- **One install, one instance per project.** Each project has its own control folder, which is a git repo. The handoff docs live there and never in a code repo.
- **Tracked control files change only through conductor's request/apply step.** The tamper guard reverts anything else that happens during an executor run.
- **The planner never deletes.** It writes `signals/` files (read mark, `clear`, `approve`, `cancel`, `reorder`, `reviewed`, `tell`, `run`, `stop`), and conductor consumes them. The app acts through the same signals, so every change to a queue is a logged event.
- **The ask tool is the executor's judgment.** The executor decides whether a question blocks or falls back to a default after 10 minutes. There are no phone notifications; desktop toasts only.
- **Approval.** Matt approves what enters `queue/`. Items in `proposed/` wait for him. A `readonly` item may go straight to the queue.
- **Staging is a resumable session:** a read-only orient phase first, then the same session resumes when it holds the lock.
- **Concurrency within a repo is declared, not judged.** It uses disjoint `paths:` plus per-item worktrees, with serial merges.

## Phases

1. Core: queues, executors, event log, inbox, tamper guard, requests, restart rule. **Done** (`reports/01_core_report.md`).
2. The ask tool, toasts, `conductor init`, and status definitions. **Done** (`reports/02_ask_report.md`). A blocking ask outlives Claude Code's 30-minute silent-call abort through a per-server timeout and 60-second progress pings (README *Long tool calls*).
3. Worktrees and staging: per-item worktrees, serial merges, `paths:` concurrency, stage-then-resume. **Done** (`reports/03_worktrees_report.md`).
4. The app: a PySide6 tray app with Repos, Questions, Events and Proposed panels, reading `events.db`. **Done** (`reports/04_app_report.md`).
5. The first real project, a roguelike deckbuilder, started from a fresh claude.ai session with `claude-ai-new-project.md` alone. Its first sessions are the test of that file. Gaps it finds come back here as *Open* lines and become conductor prompts.

## Open

- Tamper during concurrent runs ends every running item red, because conductor can't attribute it. This is acceptable while tamper never actually occurs. `paths:` concurrency makes concurrent runs in one repo more common.
- Each code repo's `CLAUDE.md` must say "commit to the branch you are on", not "commit to `main`". The sandbox's was changed. Any real repo's first prompt carries this.
- `setup` commands run inside the daemon loop, so a slow setup delays everything else for that long. This is fine for `uv sync`-sized steps. Move setup into a launcher if a project needs minutes.
- A fast-forward of the main checkout interrupted mid-write (the daemon killed during `git merge --ff-only`) leaves tracked files dirty. The merge then holds as "uncommitted changes" until Matt resets the checkout. It is rare and needs a person.
- Clicking a toast does not open the app. Toasts use Command Prompt's app id; a registered `conductor-app:` URI plus `launch_action` would likely work but needs a human click to prove.
- No report finished before `reviewed:` existed has a `reviewed` event, so on a live project (Corelight) every earlier report lists as unreviewed until the planner marks it once (several `reviewed:` lines per file, or **process all**).
- A message reaches an executor only after a tool call ends: never during one long command or a blocking `ask`, and never after its last tool call (it is logged undelivered). If that bites, the fallback is streaming user messages into `-p --input-format stream-json` stdin, which would change how executors are launched.
- The app probes each run target over HTTP on the UI thread every refresh (0.3s timeout). On Windows a closed local port can take that long to refuse, so a project with several down targets makes the app sluggish. Move the probe to a worker if that shows.
- The app's refresh still re-reads every `finish`, `red`, `clear` and `reviewed` event each tick through `state.scan`. Fine at hundreds of events; revisit if a project's log grows into the tens of thousands.
- Only the latest checkpoint shapes the views; there is no per-checkpoint history browser beyond the Events tab with *since checkpoint* off, or `conductor events --since checkpoint N`. The Repos tab's earlier group shows the 10 newest settled items per repo; older ones are reachable only through Events or `conductor open`.
- A leftover worktree is retried only at daemon start and when its repo's queue empties (never for the item that just emptied it). A project whose queue rarely empties while a stray dev server runs keeps the leftover, with one `warning` per retry, until the next start. Add a periodic retry if that shows.
- A running executor can't be switched into ultracode: no mid-run route works in 2.1.302 (README *Ultracode*). If Claude Code gains a runtime control (the Agent SDK's settings control request is the documented one), it would need executors launched through `--input-format stream-json`, the same change the message fallback above would make.
- The merge executor's checks are structural: markers gone, nothing else touched, the rebase left as found. Whether it kept both sides' *intent* is judged only by reading the result. In the sandbox it kept both rewrites of one README sentence by joining them with a semicolon, which is faithful but clumsy, and a later audit flagged that sentence as reading like a merge. A real project's first few `resolve` events are worth a look.
- A Drive-homed folder's main-checkout junction (*Storage*) is made by an executor whose preamble forbids touching the main checkout, so that item's prompt has to override the preamble explicitly. If executors balk, conductor could make the junction itself from a `shared` entry that names a target folder.
- A cleanup inlines every unused note into its prompt, with no size cap. Notes are short in practice, but a repo that collects dozens before a cleanup could send a very long prompt. If that shows, cap the count per cleanup (oldest first); the rest stay unused for the next one.
- A cleanup's deferred design calls live only in its report's **Deferred** section; nothing tracks them past **process X**. If they start getting lost, they could become a standing inbox section like *Unreviewed reports*.
- A forwarded launch raises the running app's window through `AllowSetForegroundWindow`; Windows' foreground rules may still only flash its taskbar button when the launcher wasn't itself in the foreground (e.g. started from a Claude Code shell). Needs a human look; the folders are added either way.
- `picks/` joined the runtime paths, so every control folder made before prompt 13 (the sandbox, Corelight, Word Warriors) logs a startup `warning` until a request adds `picks/` to its tracked `.gitignore`. That is each project's planner's job; conductor prompts never touch a real control folder.
- The picker server lives in the daemon's memory: a restart loses its port and token, so an open picker tab cannot save until `pick:` is sent again (the page says so and keeps its choices). If restarts mid-pick become common, a fixed port and a token kept in `.conductor/` would let tabs survive.
- The picker opens with `webbrowser.open`; under a daemon started by the app (`pythonw`-launched, no console) the browser may come up behind other windows. Needs a human look.
- The app's Repos tab picks up a **Pick…** button per finished item whose report named a manifest (amber until saved), with the pick state in its note. Check the button column still fits three buttons (Pick…, Open in terminal, Mark reviewed) on an unreviewed row.
- `uv run conductor app` runs `.venv\Scripts\conductor.exe`, which stays locked while the app is open. Any `pyproject.toml` change then makes every `uv run` fail ("failed to remove … conductor.exe: Access is denied") until the app is closed. Launching it as `uv run python -m conductor app` would avoid the lock (the daemon already runs as `python -m conductor run`); the CLAUDE.md "launch the conductor" line would change with it.
- `template: disk_audit` and `template: claude_md_cleanup` are proven only with the fake executor. A real project's first disk audit is worth a read before acting on its **Deferred** list, especially that it removed junctions as links and left worktree folders alone.
- Log compaction is lossy by design: a finished item's `.log` loses the base64 of images it read and `originalFile` copies (README *Log compaction*). The full session stays in Claude Code's store, so `conductor open` still has everything, but only for as long as Claude Code keeps it.
