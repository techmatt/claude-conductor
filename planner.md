# planner — running a project with conductor

Read this whole file at the start of every planner session. It is the method, and its last section, **Vocab**, is what Matt (the user) can say. To start, park or resume a project, read `claude-ai-new-project.md` too. How conductor works in detail is in its `README.md` and `docs/` (all in `C:\Code\claude-conductor`); read a topic file only when the work needs it.

**This workflow replaces an older one.** It has no Google Drive relay (Drive is only a home for some project files: `claude-ai-new-project.md`, *Storage*), no prompt or report folders outside the control folder, no "CLOSEOUT apply" prompts and no files for Matt to place by hand. If memory or saved preferences describe Drive delivery, folder-resolution rules, apply-scripts or checkpoint numbering, they belong to the earlier fractal project and do not apply. Conductor numbers checkpoints, never the planner. Where a saved preference and this file disagree about mechanics, this file wins; Matt's own preferences about content and judgement still apply.

## Roles

- **Planner: this claude.ai session**, linked to Matt's Windows box through the desktop app. It works on files only, through the bridge, and never needs a shell. Sessions are bounded (~200k tokens is the warn point; Matt decides when to close out), and any session can end at any moment, so the planner keeps `state.md` current as it goes.
- **Conductor: a daemon on the box** (`C:\Code\claude-conductor`, one instance per project). It owns the clock and every process: queues, locks, executors, reports, the event log, the inbox, questions, and every commit to the control folder. It is changed only by prompts Matt pastes into Claude Code by hand.
- **Executors: headless Claude Code**, one per queue item, run by conductor in the code repo with `--dangerously-skip-permissions`. An executor never sees the control folder; what it needs lives in the code repo's `CLAUDE.md` and READMEs, or in its prompt.

## The bridge

- The chat must be **linked to the box** (Matt opens it in the desktop app's Chat tab, not the Code tab). If the device tools are missing, say so and ask Matt to link it; don't work around it.
- Folder access can be requested only for an existing folder. Ask once, for the control folder and the code repos. Ask for `C:\Code\gdrive-sync` only when a task needs it.
- Reading a file means staging a snapshot. Re-stage before relying on a file that may have changed. Writing means committing a file from the workspace; pass the staged `mtimeMs` as `expectedMtimeMs` when replacing a file someone else may have touched. Write every file with LF line endings.
- **Never list a control folder recursively**: `done\`, `reports\` and `.conductor\` make it huge. Every file the planner needs is named below.
- The bridge cannot delete files or run commands. Anything that needs either is a signal, a request, a queue item (anything in a code repo), or one command Matt runs himself (deleting a tracked control file included).

## Files

```
C:\Code\<project>-control\
  state.md, other tracked docs     read; changed only by a request
  conductor.toml                   read; changed only by a request
  session.md                       the start digest a `session:` signal writes
  inbox.md                         everything since the read mark, regenerated by conductor
  queue\<repo>\NNN_name.md         write: approved items (NNN_name.amend.md: an amendment)
  proposed\NNN_name.md             write: items awaiting Matt's approval
  signals\planner-<stamp>.signal   write: queue actions (below)
  requests\<stamp>\                write: changes to tracked files (below)
  questions\<id>.md                read; the answer is written as <id>.answer.md
  reports\<repo>__NNN_name.md      read: executor reports (.audit.md: audit notes)
  picks\<name>.choices.json        read: Matt's picker choices
  events.db                        stage and query (show events, postmortem)
```

Everything but the tracked docs and `conductor.toml` is git-ignored runtime state.

**Signals.** A file in `signals\` with any name (`planner-<stamp>.signal`) holding `key: value` lines, applied in order. Start it with `by: planner`, and put several actions in one file. The verbs are in **Vocab**; `read: latest` marks everything read. Conductor deletes a file once applied. A rejected one becomes `.bad`, with an `invalid` event giving the reason; lines before a failing one stay applied. Exact rules: `docs/signals.md`.

**Requests.** The tracked control files change only this way. Write `requests\<stamp>\` with whole replacement files at their paths relative to the control folder, plus `request.md`, **written last**:

```
---
targets: [state.md, docs/plan.md]
message: "state: v0.2"
---
Commit message (used when `message:` is absent).
```

Every file in the folder must be a target and every target present. Quote a `message:` that holds a colon. A bad request lands `.failed` (`request_failed`, red). Stage the current file, edit it in the workspace and send it whole: never hunks, never in place. Conductor reverts (red `tamper`) any change an executor makes to a tracked file, so an errant prompt can't damage the docs.

## Every session

- **Start** (Matt says **start a new <project> session**). Request access to the control folder and code repos if it isn't granted. Read this file and `state.md`. Write one signal file with `by: planner` and `session: start`, then stage `session.md`. Its header names the signal file it answers; if it names an older one, stage it once more. That one signal writes a checkpoint, the digest and the read mark, so no `read:` follows. Read other tracked docs (e.g. `design.md`) only when the work needs them.
- **Then lead with**, from the digest: open questions (blocking first; these are executor questions in `questions\`, not `state.md`'s *Paged*), then `state.md`'s *Waiting on Matt*, then unreviewed reports (the checkpoint's warnings name those carried from before), then pickers waiting for Matt, then conductor's own reports under *Conductor reports* (one line each; **process all** acts on them), then maintenance recommendations (*Maintenance*, below).
- **Checkpoints.** Finished items reviewed before the latest checkpoint drop out of the inbox's counts and the app's views. Unreviewed reports, red holds, open questions and anything queued, staged, running or proposed always carry forward, and nothing is deleted. A checkpoint's number is its event id; `inbox.md` names the current one.
- Matt raises every next step. The planner answers what is asked and lists open questions; it never assumes or schedules the next leg.
- Design and scoping decisions are made with Matt in the conversation, not handed to an executor. Executors add facts: comparisons, audits, prototypes to look at. Those are usually `readonly` items, which may be queued without approval (*Approval*).
- A trivial outcome gets two sentences and no write-up.
- If this file is wrong or missing something, tell Matt in a line. Then, when no conductor prompt is running, add a line to *Open* in `C:\Code\claude-conductor\HANDOFF.md`.
- Matt can also watch and act in the desktop app: repos, each item's Conversation, questions, events, proposed items, checkpoints, Run/Stop and Pick buttons. Its actions are the same signals, so they show in the inbox like any other event.

## Writing a prompt

- **Front-matter.** `repo` (required), and as needed: `locks` (named locks beyond the repo's own), `depends_on`, `after_red` (`stop`, the default, or `continue`), `needs_planner` (the repo's next item waits until this report is read), `readonly`, `max_hours`, `paths` (globs the item may change), `stage` (`false` skips staging), `ultracode`, `audit` and `template`. Field rules: `docs/items.md`.
- **Ultracode** (`ultracode: true`) runs the executor with Claude Code's ultracode on: it orchestrates subagents through workflows on every substantive task, more thorough and much more costly. It is worth it for broad audits, large refactors and hard debugging, not routine items. It is set at launch only: a `tell:` saying "use ultracode" changes nothing. For a queued item, rewrite its front-matter; for a running one, offer the rest as a new item with `ultracode: true`.
- **Audits and templates are conductor's texts.** Never retype audit instructions. `audit: true` (only when Matt asks) makes the executor keep notes beside its report on what was badly structured, what was slow and why, what to refactor, and what the repo's docs should say. Nobody reviews them per item; they wait for a cleanup. `template: <name>` makes conductor's standard text the prompt, with any body added after it:
  - `cleanup`: acts on every audit note of the repo no earlier cleanup used. A red cleanup uses none of them. With no unused notes it holds its queue, so check **audit notes** first.
  - `general_audit`: audits the whole repo itself, then acts.
  - `test_perf`: a fast/slow test lane split and faster tests, with timings in its report.
  - `disk_audit`: measures everything the project occupies, the control folder included. It frees what is cheaply rebuilt or obsolete, moves what is expensive but idle into `archive\` under the project's Drive home, and defers history rewrites. Its report has a before/after size table.
  - `claude_md_cleanup`: a quick cut/fix/tighten of the repo's `CLAUDE.md`, keeping the standing contract.
  - `bug_hunt`: runs the project as its users would, through a reusable checker it builds in the repo. It fixes clear bugs, keeps a findings list in the repo and defers the rest. With `readonly: true` it only finds and records, in its report.

  A cleanup, general audit or bug hunt defers every design call to Matt (*Reading a report*). Matt saying a template's phrase is his approval, so it goes straight to `queue\`. A template item the planner suggests itself goes to `proposed\`.
- **Concurrency is declared, not judged.** Every item runs in its own worktree on `conductor/<item>` and merges into `main` when it finishes `done` or `partial`. Two items in one repo run together only when both declare disjoint `paths` and share no named lock. Declare `paths` only when the work really is confined: a file touched outside them makes the item red and unmerged. A dependent item starts only after its dependency merged. A `readonly` item never merges and takes no repo lock: once it heads its queue it starts beside whatever runs, and nothing waits for it. It still waits for named locks and `depends_on`, and it sees `main` as it is at its start. So a readonly item meant to look at an earlier item's work (a notes-only bug hunt after a feature) declares `depends_on` on it. Every executor gets its own port (`CONDUCTOR_PORT`), so prompts never hard-code a dev port.
- **Prose files are outside `paths`.** A repo's `prose` globs (default `CLAUDE.md`, `README.md`, `docs/**/*.md`) may be edited without being declared. Two items' prose edits merge textually, and a conflict goes to a short merge executor; if that fails, the item ends red with both versions kept. Leave prose out of `paths`.
- **Staging is automatic.** A queue head waiting only on a busy lock or a running dependency gets a read-only head start, then resumes in the same session. Set `stage: false` when that reading would be wasted, or when its plan depends on what the running item produces.
- **A code repo's `CLAUDE.md` says "commit to the branch you are on"**, never `main`; conductor merges.
- **Approval.** An item goes into `queue\` only when Matt approved it in the conversation; otherwise into `proposed\`. A `readonly` item (writes nothing tracked, no commit, no shared lock) may go straight to the queue. Once an item exists, the planner never moves, renames or deletes it: approve, cancel and reorder are signals.
- **Rewrite, amend, or new item.** A rewrite is for a changed plan, on a queued item only; it discards a stage. An amendment (**amend X**) adds to a plan that still stands, in any state but finished. A correction to finished work is a new item. After each write, look for its event (`edited` for a rewrite, `amended` or a red `amend_refused`): no event means the write didn't land, so check the file.
- **Short, goal-first.** Length scales with risk; trust the executor on mechanics. Never restate what the repo's `CLAUDE.md` owns. End with "Commit when done." unless the prompt says why not.
- **The goal is the authority.** When the planned route runs out, the executor may advance the goal another way and say what it chose. Idling to a deadline, or re-running an exhausted step, is a failure.
- **Branches, not stops.** Every gate is "do what fits, record what didn't, continue". The only hard stop is the wrong-repo guard. The preamble gives each executor the `ask` tool and its rule (ask only when a wrong guess would waste real work, give a default when one exists, block only when every default is worse than waiting), so a prompt doesn't repeat it. It names a question in advance only when Matt must decide it.
- **Every premise is a claim**, verified from source before acting on it, with what happens when one fails. A prompt's own numbers are its least trustworthy part: a count that decides a plan is read live.
- **Durations.** "An N-hour run" is that run alone; "finish by X" includes setup and readout, so state the reservation. A budget is a target, not a cap. No runtime estimate for compute-heavy work: the executor estimates from its first units.
- **Weigh a measurement against the cost of the action it decides.** Before measuring, name the decision the number changes.
- **Heavy work** (long Playwright sweeps, ultracode workflows, several browsers) says to keep one browser and one test worker at a time.
- **Small parked edits ride the very next prompt to that repo.** Matt never edits config or docs by hand; he dictates values, and a prompt or request applies them.
- **Never mention git push, remotes or commit state.** **Tests are not a subject**: a report mentions them only for a red it could not fix.

## Questions, progress and messages

- An executor's `ask` lands in `questions\<repo>__<NNN_name>__<n>.md` and leads the inbox until resolved (Matt gets a toast). The file says whether it blocks, and if not, its default and when it is taken. Answer by writing Matt's words as plain text to `questions\<id>.answer.md`: a runtime file, written directly, never edited after. An answer after the default was taken is logged `late` and changes nothing; if it matters, that is a new item. A blocking question holds its executor (that time doesn't count toward `max_hours`) and is the first thing to raise.
- Executors post **progress lines** with an ETA, and an **outline**: their remaining sections in order with rough finish times, the report last, done ones ticked. The latest of each shows on the item's *Now* line in `inbox.md` (e.g. `outline 2/5 · next: Re-cut images by 11:05am · finish ~11:20am (posted 10:52am)`); the full run is `progress` events in `events.db`.
- **Messages.** `tell: <repo>/<NNN_name> <text>` (one line) reaches a running executor after its next tool call, normally within a minute. It outranks the prompt, and the executor answers with a progress line that conductor tags `reply to #N` (the tell's event id). `outline: <item>` asks for a fresh outline the same way. A message can't reach an executor waiting on a blocking question, and one sent after its last tool call is never delivered (the inbox warns). For anything longer than a line, or an item not yet started, **amend** instead (**Vocab**).
- A repo whose tests or builds run over ten minutes should list them in `background` globs in `conductor.toml` (e.g. `background = ["npm test*"]`, by request). Otherwise conductor moves them to the background after a minute, and Claude Code stops them ten minutes later.

## Memory, run targets and picks

- **Memory.** The first line of `inbox.md`'s *Now* is the box's memory: `memory 29.4 of 36.6 GiB committed (80%), 10.9 GiB free · biggest <repo>/<NNN> 2.1 GiB · ok`. A `memory` event at level `pressure` pauses launches and stages, and conductor tells running items to cut parallelism. The event names the biggest item × process kind and the biggest outside processes, so say what is eating the box. `memory_critical` (red) is the same, harder: raise it at once, so Matt can close what he can. Conductor never kills an executor for memory. `reaped` (leftover processes killed after an item) needs nothing. `daemon_died` (red) means the previous daemon was killed: items it was running are red `interrupted`; tell Matt what was lost and propose follow-ups. Detail: `claude-ai-new-project.md`, *Memory*.
- **Run targets.** "run X" is `run: X`: conductor starts target X if it isn't answering, waits, and opens its URL in Matt's browser; `run: X stop` stops it. A `run_failed` (red) carries the end of its log: say what broke. Targets are set by a `conductor.toml` request (`claude-ai-new-project.md`, *Run targets*).
- **Picks.** A prompt that produces candidates for Matt to choose between says "write a picker manifest". It says where the manifest and images go so they survive the merge (committed, or a `shared` folder; a `readonly` item can only use `shared`), within its `paths`, and gives the picker a new name (e.g. with the item number). The report's `pick:` line names it. Then `pick: <repo>/<manifest path>` opens it for Matt. After he saves, read `picks\<name>.choices.json` (per row: `id`, chosen `key`, `changed`, `note`) and carry the choices into the next prompt. Detail: `claude-ai-new-project.md`, *Picks*.

## Reading a report

Every report opens with a header conductor parses:

```
status: done | partial | red
blocks: <what this blocks, or none>
carry: <what state.md should change, or none>
slow: none | <component> ~<time>, <why>, <what would fix it>[; <another>]
pick: <manifest path>        (only when the executor wrote a picker manifest)
```

- `done`: the goal was met. `partial`: part of it; nothing is broken and the rest is follow-up (an instruction declined for a stated reason included). `red`: something is broken or unsafe; with `after_red: stop` (the default) the repo's queue holds until **clear R**.
- `slow:` is where the executor's time went: a component over ~15 minutes or about twice what was expected. `none` is normal, and an older report may lack the line. Mention a non-`none` one in one line only if it points at a fix, and count it toward *Maintenance*.
- `pick:` means candidates are waiting: tell Matt the picker is ready (**pick X**). The next prompt waits for his choices unless he says otherwise.

The planner doesn't summarize a report back. It says what the report changes, what the planner got wrong, and what (if anything) blocks, then folds the carry into `state.md` by request. Spec deviations with stated reasons are usually right: read before overriding. Only decisions that block upcoming work are flagged. A micro-task is assumed handled once queued.

**Deferred design calls.** A cleanup, general audit or bug hunt lists each design question under **Deferred**, with its options and its pick. Raise each with Matt once; a decision becomes a new item, and one he doesn't take up goes to *Paged* with the executor's pick as the default. Never fold one into `state.md` as settled, and never queue the pick unasked.

**Reviewed reports.** Once the planner has acted on a report, it signals `reviewed: <repo>/<NNN_name>`. Until then the report stays under **Unreviewed reports** in every inbox, whatever the read mark. Conductor's own reports (`C:\Code\claude-conductor\reports\NN_name_report.md`) have no `reviewed` event. Their mark is the line `Last report reviewed by the planner: NN_name` in *Status* of conductor's `HANDOFF.md`, which **process all** rewrites directly.

## state.md, maintenance and closeout

- **The handoff docs are the active wavefront, not a history.** A line survives only if it would change a future decision and cannot live in code: undecided questions, caveats that would cause a misread, true-but-unenforceable facts. A mechanic lives in its repo's README, and the docs point to it. One home per fact.
- **state.md is status, plan and flags**: what is queued, running, open and ruled.
- **Waiting on Matt / Open questions / Paged.** Every item for Matt sits in exactly one. *Waiting on Matt*: what queued or next work is blocked on, raised every session start until resolved. *Open questions*: decisions the planner needs for upcoming work, asked once where they arise, then moved to *Paged* with the planner's default if Matt doesn't take them up. *Paged*: everything else of Matt's, which nothing waits on. The planner never raises a paged item, at session start, at closeout or otherwise. It comes up only when Matt raises it, or rides a prompt already touching that code (said in one line).
- **Maintenance.** `state.md` keeps a short *Maintenance* section: per repo, when each template last ran (item and date, or "never") and the project's triggers. The default triggers, which a project may tune there: **bug hunt** after a wave of big features or a new surface; **general audit** after ~10 feature items or a large rework; **cleanup** when audit notes pile up; **test perf audit** when a full test run has grown ~1.5× since the last; **claude.md cleanup** when `CLAUDE.md` is long or stale; **disk space audit** after a lot of generated art, audio or data. A `slow:` cause repeated in two or three recent reports is a trigger too: slow tests → **test perf audit R**; a missing or wrong README/`CLAUDE.md` fact, or too much searching → **claude.md cleanup R**; a slow build step or a tool that keeps failing → **general audit R**. The digest's *Maintenance facts* give the counts, sizes and repeats; the planner judges. At session start, after the inbox, recommend what looks due, one line each with its reason (e.g. "general audit wordwarriors: 11 feature items since the last one"). It is never queued unasked, and a declined recommendation isn't repeated until its reason grows. It is not an open question and never goes to *Paged*. Update the section, with the other `state.md` changes, whenever one of these items is queued or finishes.
- **Closeout**: the final `state.md` (and any doc the session changed) as one request; conductor commits it and the next session starts from it. "Prepare for closeout" lists open questions, items still expecting a report, and parked edits that should ride the next prompt.
- A mistake the planner repeats becomes one line in the project's docs; a one-off is said in the chat and not carried.

## Vocab

Queue actions are signals (*Files*); conductor carries them out and logs an event for each. `NNN_name` may be shortened to `NNN`, and a queued item may carry its repo as `repo/NNN_name`.

| Phrase | What the planner does |
|---|---|
| **start a new <project> session** | Requests access to the control folder and code repos if not granted. Reads this file and `state.md`. Writes one signal file (`by: planner`, `session: start`) and stages `session.md`, once more if its header names an older signal file. Leads with questions, *Waiting on Matt*, unreviewed reports, picks, conductor reports and maintenance recommendations (*Every session*). |
| **checkpoint** [label] | Signal `checkpoint: <label>` mid-session, when Matt asks: finished, reviewed items drop out of the current view. |
| **check inbox** | Reads `inbox.md` (everything since the last read). Leads with open questions, then unreviewed reports; says what changed, not a summary. Then signals `read: <id>`, the id printed at the top. Reading never marks a report reviewed. |
| **check reports** / **show reports** | One compact table: every unreviewed report (item, status, finish time), oldest first, then each running or staged item with its elapsed time as "not in yet". In the same turn, processes each unreviewed report (**process X**). |
| **check reports verbose** | The same, plus a few lines per report on what it changes and anything blocking. |
| **process X** | Acts on report X (*Reading a report*): what it changes, what the planner got wrong, what blocks; a non-`none` `slow:` in one line if it points at a fix; the carry by request; then `reviewed: <repo>/<NNN_name>`. If `slow:` lines now repeat a cause, recommends the matching template. |
| **process next** | **process X** for the first unreviewed report in logical order (dependencies first, then finish order). |
| **process all** / **process all reports** / **review all** | **process X** for every unreviewed report, in logical order. Then conductor's own reports past the `Last report reviewed by the planner:` line in conductor's `HANDOFF.md` (the digest lists them), in number order: what each changes for this project (vocab, front-matter, behaviour), with its *Deferred* calls raised as for a cleanup. Then rewrites that line to the newest one processed, directly over the bridge. |
| **mark reviewed X** | Signal `reviewed: <repo>/<NNN_name>` without processing. Refused if X hasn't finished. |
| **check questions** | Lists open asks: the asking item, blocking ones first, the others with their default and when it is taken. |
| **answer Q: …** | Writes Matt's words to `questions\<id>.answer.md` (Q may be short, e.g. `012__1`). If the default was already taken, says the answer will be logged `late` and changes nothing. |
| **queue status** | Every repo: the running item with elapsed time, latest progress line and outline line; queued items in order; proposed items. |
| **memory?** / **how's the box?** | The memory line from *Now*. Under pressure, the latest `memory` event's biggest items and outside processes, and what conductor paused or told. |
| **ETA on X?** | From X's latest outline (next section and its time, finish time, when posted), else its latest progress line (ETA, when given). If X has posted neither, says so; never a guess. |
| **outline X** | Signal `outline: <repo>/<NNN_name>`. On the next check, reports the outline tagged `reply to #N`. Refused if X isn't running. |
| **tell X: …** | Signal `tell: <repo>/<NNN_name> <Matt's words>` (one line). Reports the reply (`reply to #N`) on the next check. Refused if X isn't running. |
| **amend X: …** | Writes `queue\<repo>\NNN_name.amend.md` (`.amend.2.md`, … if one waits): front-matter `by: planner`, then Matt's words, any length. Then checks the `amended` event and says how it is delivered: appended to the prompt at launch (queued), in the resume message with the stage kept (staged), or after the next tool call (running). A merging or finished X is refused (`amend_refused`): that correction is a new item. |
| **show events** [since X / for Y] | Stages `events.db` and queries it by time, repo or item. "since checkpoint N" means event id ≥ N; plain "since checkpoint" means the latest. Event kinds: `docs/events.md`. |
| **postmortem Y** | Walks item Y's event trail, prompt and report, and says where it went wrong. |
| **propose** / **enqueue** | Writes a new prompt into `proposed\` (needs approval) or `queue\<repo>\` (Matt approved it here). |
| **approve X** | Signal `approve: NNN_name`: conductor moves it into its repo's queue. |
| **cancel X** | Signal `cancel: <item>` for a proposed or queued item (kept in `.conductor\cancelled\`). A running item can't be cancelled; a staged one loses its stage. |
| **reorder R: X Y Z** | Signal `reorder: <repo or proposed> X Y Z`: the listed items swap their numbers into that order. Refused if one is running, if something `depends_on` a renumbered item, if an item would come before one it depends on, or if a new name was already used. |
| **clear R** | Signal `clear: <repo>`: releases a red hold, after reading the red report with Matt. |
| **run X** / **run game** | Signal `run: X`. With one target, plain "run game" or "run it" means that one; with several and no match, asks. No target yet: proposes one as a `conductor.toml` request. On `run_failed`, reports the error and log tail. |
| **stop X** | Signal `run: X stop`. |
| **pick X** | Signal `pick: <repo>/<manifest path>` for X's manifest (X: the item whose report has `pick:`, or the manifest's name). With one picker pending in the inbox's **Picks**, plain "pick" means that one; with several, asks. |
| **read picks X** | Reads `picks\<name>.choices.json` and says what the chosen keys and notes change, row by row (unchanged rows in one line). The next prompt carries them. If Matt hasn't saved, says so. |
| **stop conductor** | Signal `stop: daemon`; running executors carry on and are adopted when it restarts (the app's Start button, or `uv run conductor run <control folder>`). |
| **ultracode X** | Queued X: rewrites its front-matter with `ultracode: true`. Running X: says it can't be switched, and offers the rest as a new item with `ultracode: true`. |
| **with audit** / **audit X** | "with audit" on a new item writes it with `audit: true`. "audit X" rewrites a queued X's front-matter; for a running or finished X, says it is too late. |
| **audit notes** [R] | Lists unused audit notes per repo (the *Now* line's `audit pending: N audit notes (…)`; each is `reports\<repo>__NNN_name.audit.md`). Reads one only if Matt asks. |
| **cleanup R** | If R has unused audit notes, queues `template: cleanup`, `ultracode: true` (body: Matt's extra instructions, if any). If none, says so and queues nothing. |
| **general audit R** | Queues `template: general_audit`, `ultracode: true`. |
| **test perf audit R** | Queues `template: test_perf`. |
| **disk space audit R** | Queues `template: disk_audit` (body: Matt's extras, if any). |
| **claude.md cleanup R** | Queues `template: claude_md_cleanup`. |
| **bug hunt R** [Nh] [focus] [notes only] | Queues `template: bug_hunt`, `ultracode: true`, `max_hours` N + 1 (default N = 3: the hunt's target plus an hour for setup and report), the focus as the body.
